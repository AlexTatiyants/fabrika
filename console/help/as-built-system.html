The system map groups your files into subsystems by what depends on what, and shows how the subsystems connect. Open one to see what's inside it, and a file to see what it does.

Reading the map

Each box is a subsystem, with a three-letter ID that stays the same across readings, and the same ID is used on the Capabilities page. A line means files in one subsystem import files in the other, and the number is how many. Dashed lines include links the reader reported and the code didn't confirm. Point at a subsystem to bring its links forward; select it to open it.

With many subsystems the map becomes a grid with one line for each pair, so it stays readable.

Product and support

Product subsystems are the ones a capability reaches: code a person's action ends up running. Support subsystems (build, configuration, environment) are reached by nothing a person does. They're listed apart so they don't crowd the picture.

Shared files

A few files are imported by nearly everything. Drawing them would put a line from every box to one point, so they're left off the map and listed underneath instead.

A subsystem's page

  • How it connects: what uses it, and what it uses.
  • Inside it: a map of its files, grouped by folder.
  • Files: what each is for, and whether any test reaches it.
  • Capabilities that pass through: the ways in that run code here.

A file's page

What the file is for, what it connects to, the ways in it carries, the capabilities that reach it, the tests that import or call it, its functions, the data it defines, reads and writes, and what it talks to outside the repository. A function opens the source at its line. No test imports or calls this file means exactly that, not that it's untested in every sense.
