Fabrika tests everything it builds. For that to work, your repository needs a way to run a test, clean up after it, and run it again with the same result.

Why tests have to be repeatable

Fabrika is designed to validate the code it builds automatically, often while nobody is watching. It writes tests for each acceptance criterion and runs them, again and again, as it builds and repairs. A test that leaves data behind changes what the next test sees, so a failure can be the leftovers rather than the code. Fabrika can only trust a result if every test sets up what it needs and tears it down afterwards.

What the survey looks for

  • Test runners at three levels: unit (logic on its own), integration (your app's own interfaces), and user (the whole system, the way a person uses it). See Test levels.
  • How tests set up and clean up at each level: a fresh database per test, each test working in data it creates, fakes undone after every test, and so on. See Setting up and cleaning up.

Where either is missing, the survey proposes a fix.

When the fix is in your code

Some fixes need changes Fabrika won't make on its own, like an API endpoint that lets a test create its own data. For those Fabrika gives you a ready-to-use prompt. Hand it to your coding agent, commit the change, and re-survey. See When Fabrika asks you to change your repository.

If a level can't be checked

You can say no to any fix. Fabrika still builds features, but it won't check acceptance criteria at a level that can't run tests cleanly: it would only produce failures that say nothing about the code. Those criteria are marked on the spec before you freeze it, and at review they arrive as a checklist for you to check by hand. See When a level isn't checked.
