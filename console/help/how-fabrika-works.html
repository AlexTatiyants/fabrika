You say what a feature should do, and you rule on what comes back. Everything in between is done by model agents, in a fixed order that plain code decides.

Three places you decide

Repo readyaccept a project's checks, once
→
Spec reviewanswer the questions, approve the spec
→
The buildagents build, test, review and repair
→
Feature reviewrule on the review packet

Nothing asks for your input while a build runs: a review you could click through mid-run would stop being a review. The one exception is plan review, and it happens only when two agents disagree about how to cut the work. See Plan review.

What comes back

Not a pull request. A review packet: the code, on a branch of its own, and a structured argument that it does what the spec asked. Acceptance tests written from the spec by an agent that never saw the code, your project's own checks, a review panel's objections, and what the repair loop did about each. You audit the argument and rule on what it leaves you, rather than reading every line.

Every feature is built in its own worktree, on its own branch. Your checkout is never written to, and every agent and check runs in a sealed container.

Where things are

  • yard: your projects, and where you add one.
  • crew: the agents, the models they run on, and the accounts that pay for them.
  • control room: settings that belong to you on this machine.
  • help: this. Press ? on any screen to open the topic for it.

The rail on the left lists every project and its features in flight; Needs you narrows it to what is waiting on you, and [ hides it.
